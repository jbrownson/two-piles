Two Piles of State

Every UI has two kinds of state. Most keep them in two piles.

To write · opening

  • What the figure shows: the state that isn’t app data, such as focus, caret, selection and scroll.
  • Each pile can change without the other, and the two don’t live equally long: quit and relaunch, and app state comes back from disk while the UI state starts over.
  • The problem, in a few sentences: the screen has to follow both piles. Every change to either one must reach it, and a change to app state often has to take UI state along. Delete a row, and the caret should stay with the text it was in.
  • Why it’s worth stating: new UI frameworks keep arriving, which suggests the problem is still open. It is also seldom spelled out, the UI-state half least of all.
  • End on the two questions below. They are the yardstick for everything after: the first two lines under every figure, and the table at the end.
  • Tone: no one got this wrong. It is a hard problem with several good answers, and the aim is to describe them all in the same terms.
  • Aside, keep it short: the split into two piles is usually taken as a given (a lobste.rs reply: “the GUI has its own state that isn’t application state…”). One pile is reasonable too, as in a truly immediate mode, but it isn’t the subject here.

Retained mode: every handler edits both piles

Mac Toolbox · Win32 · Swing · jQuery

To write · retained mode

  • What to notice: the handler has the change in hand, so nothing needs matching and the caret never moves.
  • The other side of that: the data and the screen each get their own line, and the toolkit can’t check one against the other. The figure’s switch leaves one line out to show what that looks like.
  • Worth saying outright: neither line touches UI state. It sits inside the widgets, which is why the caret stays put.
  • The same missing line comes back in deui, where a check catches it.
  • Be fair: decades of software were built this way, and it is fast.
  • Context, one sentence: this is the first of three answers in wide use. They arrived in this order, and none replaced the one before.
  • The same four lines follow each figure: where UI state lives, how the screen learns what changed, a strength, a trade-off.

Every figure on this page runs the script you just watched: click into a row, type, select a word, delete the row above, scroll, then quit and relaunch. Two things are worth watching, one for each question: what becomes of the UI state, and how much the screen had to do. Each figure is laid out as a diagram: what you keep on the left, the screen on the right, and between them whatever that approach puts there. The UI state pile sits with whoever keeps it. Each line of code that ran draws an arrow to the pile or the window it touched. A thin arrow is one change, a wide one is everything, and a dashed one is a path that didn’t run this time. The figures are small working models built for this page, not the real toolkits.

UI state
In the widgets. The toolkit keeps each one alive, and each holds its own focus, caret and scroll position.
Changes
Your handler passes each change on by hand: one line edits the data, another edits the widgets on screen.
Strength
Direct and fast. Each handler touches exactly what changed, and UI state never needs matching up, because it stays in the widget it was in.
Trade-off
Each change is written twice, once for the data and once for the screen, and the toolkit has no way to check that the two edits agree. If the screen’s edit is missed, the screen goes on showing what the data no longer says, until it is next rebuilt from the data. The figure’s switch leaves that line out to show it.

React: rerun everything, then diff

React · Vue · Elm

To write · React

  • What to notice: with keys and without, the two lists of writes give the same picture, and only one is what happened. A diff finds a change that explains the picture, not the change itself. Keys tell it which, and the caret is where you see the difference.
  • Be fair to what narrows the rerun: memoization and compilers. Check the details before publishing.
  • Context: React came partly in response to two-way data binding (WPF, Knockout, Angular 1).
UI state
In the DOM and in components, which React keeps from one render to the next. Keys say which row is which.
Changes
You write the view once, as a function of the data. React reruns it and compares the result with the last to work out what changed.
Strength
One description of the view, so the screen can’t drift from the data.
Trade-off
The change itself isn’t passed along, so the work follows the size of the view, not the size of the change. And because UI state lives in nodes that are kept, list rows need keys for focus and caret to stay with their items. The figure’s switch shows what the keys do.

Immediate mode: redraw everything, every frame

Dear ImGui · egui

To write · immediate mode

  • What to notice: the retained tree is gone. The widget state remains, in a store, and IDs do for it what keys do in React. Puri takes the next step.
  • Set up the key message here: all three approaches need a stable identity for every place state is stored. In retained mode it is the widget object, which has to be kept alive and kept hold of. In React it is a key. Here it is an ID. The same cost, paid three ways.
  • Context: games have long worked this way, and it has spread to tools and apps.
  • Be fair: some libraries skip frames when nothing is happening. Check the details before publishing.
UI state
In the library’s own store, under an ID your code gives each widget.
Changes
The screen never needs to know: the whole interface is drawn again every frame.
Strength
No retained tree and nothing to compare. The code that draws the interface is the whole interface.
Trade-off
Every frame is drawn in full, whether or not anything changed. Some libraries draw a frame only when something happens, and each of those frames is still drawn in full. And IDs do the job keys do: UI state stays with a widget only while its ID stays the same. The figure’s switch takes IDs from position to show it.

To write · a fourth answer? Signals

  • The best-known answer on the web to rerunning the view: Solid, Svelte 5, Vue, Angular.
  • Where UI state lives: much as in React, in the DOM and in components, with keys for list rows.
  • How the screen learns what changed: a runtime records which computations read which signals and reruns only those. For lists, it falls back to keyed diffing.
  • Your line: signals are change actions where every change is “replace this value”. That’s why they never need a proof, and why a list can’t say “insert at 3”.
  • Check each framework’s details before publishing.

A proposal

Seen through the two questions, the three answers have two things in common. UI state is kept inside the toolkit, in widgets, DOM nodes or a store, and matched to your data by identity: the widget itself, a key, or an ID. And the change, which is known exactly at the moment it happens, is then either applied to the screen by hand, or let go, with the screen brought up to date by comparing or by redrawing.

What follows takes the questions one at a time and answers each directly. Puri keeps UI state in your program, as plain data. deui keeps the change, and derives the screen’s change from it. Both have working prototypes; neither is established practice.

To write · the proposal

  • Each idea answers one question directly: Puri the first, deui the second.
  • Puri is useful on its own. deui needs Puri. Puri’s trade-off is what deui takes up.
  • Why the second needs the first: Puri makes the view a pure function of your state, and deui is that function’s derivative. You can only differentiate a function.
  • Hold the proposal to the same four lines as the others, trade-offs included.

Puri: widgets that keep no state

To write · Puri

  • Answers the first question directly: there is no separate UI state. Focus, caret, selection and scroll are fields of your one state, so how they’re held is your choice, the way layout is.
  • A key message: perhaps the biggest cost of the approaches above is that each place state is stored needs an identity that stays the same from one frame to the next. Keys and IDs are that cost. Puri doesn’t make the need go away. It makes it explicit, and yours to answer in the way that suits your app: on the item, in a keyed store, by position with care, or with a general system plugged in.
  • The figure’s switch is that choice. Its third setting, a table by row, fails the way position keys fail, and the fix is one line in your own callback.
  • Keeping no state doesn’t mean the widgets do less. Each one returns its picture and a handler, good until the next rerun. The handler does the widget’s work (which column a click landed on, what a key does to the text and the selection) and passes the result to a callback you gave it. Your callback only says where in the state it goes.
  • An objection worth quoting: “immediate mode libraries that shunt all state management onto the application are out of the question.” A reply: you pick a store, and it can be the same keyed table. The widgets just don’t pick for you.
  • Another: web developers have tried “everything in the store”, and many moved away from it. What’s different here: this goes down to the caret, and plumbing is cheap to write now. Check that history before publishing.
  • It merges the piles: there is one state, drawn in one colour. What the approaches above call UI state is here just the part you strip out when you save and build back when you load.
  • Saving in the figure is one line, disk.save(strip(s)), and a relaunch starts the focus and caret over, as in every figure above. Keeping the caret across launches would be a small change to strip, which the approaches above can’t offer.
  • Also possible: finer control over how UI elements change state, such as how multiple clicks behave. The roc-puri to-do example works this out in detail.
UI state
Nowhere separate. Widgets keep none, so focus, caret, selection and scroll are fields of your one state, shaped however suits the app.
Changes
Each widget returns a handler with its picture. On an event the handler works out the change and passes it to your callback, which writes your state, and the whole view is rerun.
Strength
One state. It can be tested, saved in one line with whatever you choose stripped out, and managed however you like. How its parts are tied to your data is your decision, in the open, not a key or an ID the toolkit asks for.
Trade-off
Everything the widgets used to keep for you now needs a place in your state and a callback that writes it there, the caret included. And widgets that draw themselves give up what the platform’s text boxes provide, such as accessibility and input methods.

That first trade-off, a hand-written edit for every part of the state a change touches, is where deui starts.

deui: keep the change

To write · deui

  • Answers the second question directly: the change is kept, not recovered.
  • The name: deui, said “dewey”. It’s dUI, the change in the UI. It also reads as de-UI, taking something away, and that isn’t wrong.
  • The change is a value. A derivative turns the state’s change into the screen’s change.
  • Identity again: here state can be kept by position and still follow its item, because the change says how the positions moved. In the figure the focus goes from row 3 to row 2. No key is needed, since nothing has to be matched up afterwards.
  • Precedent: the best text editors already work this way. CodeMirror 6 and ProseMirror carry every edit as a change and map the selection through it. They do it by hand, for one widget.
  • In retained mode a missing line went unseen. Here a derivative with a missing edit breaks the law, and a check catches it.
  • When a change and your focus collide, a policy you chose decides. No magic. The script doesn’t show this. The reader can, by deleting the row they’re in.
  • Credit Phil Freeman’s PureScript Purview (2017–18), and the story of where the idea came from.

In this figure the derivative is hand-written JavaScript, and the check reruns the view after every change to compare. In a proved version the check is a proof, done once, before the program runs. lean-puri is one.

UI state
Nowhere separate: in your one state, as in Puri.
Changes
Each change is kept as a value. A derivative turns it into the edits to the screen, and a proof shows the result equals a rerun.
Strength
The work is the size of the change, not the size of the view, and one change accounts for both the state and the screen.
Trade-off
Every view needs a derivative and a proof of it. The proof covers correctness, not speed. So far it has been done for one widget.

Which leaves a fair question: who writes all those derivatives, and why would you trust them?

Why now: you read the spec and the law

To write · why now

  • Derivatives are tedious, mechanical code. An LLM writes them and a proof checker checks the law, so you don’t have to trust whoever wrote them.
  • This isn’t specific to one prover. Any proof system would do. Lean and Bend are probably the two realistic candidates today.
  • The evidence: lean-puri, a scrolling list of 10,000 items. Per its README, a frame takes 17.3 ms drawn whole and 0.27 ms from the change, and the derivative itself takes microseconds.
  • Limits, said plainly: the proof covers correctness, not speed (lean-puri had a proven derivative that stayed slow until commit 5bda7e2), and so far it covers one widget.
  • The open question to hand to readers: do derivatives of real layout, like wrapping text and nested boxes, stay tractable?

An LLM writes the derivative and its proof, and a proof checker checks one law: applying the derivative’s change equals recomputing from scratch. Breaking it here is an illustration. The proof shown is a real one, lean-puri’s Scroll.lean, checked by Lean.
